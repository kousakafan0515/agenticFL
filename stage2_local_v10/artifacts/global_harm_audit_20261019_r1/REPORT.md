# V10 Global1 / Global3 逐题伤害审计

只读分析。以同客户端、同一 `game_file` 的冻结134题逐题配对：B2→Global1、B6→Global3。前者成功、后者失败记为一次“伤害”。这表示**结果翻转**，不自动证明某条 Skill 导致失败。12份验证 `result.json` 的 SHA-256 与各自 `summary.json` 相符，均为134题、API-clean；同客户端两次比较的题目身份与任务类完全一致。原始库、结果、控制器均未改动。

## 被注入的 Skill 与角色

逐题 `result.json.episodes[].skill_injections` 同时记录角色、实际注入的 Skill key、ID、文本字符数及 `display_id_map` 来源。本审计将其逐一与相应 Global 原库校验；**注入是暴露证据，不代表该角色遵循了 Skill**。每端角色如下：A 为 Planner、Executor；B 为 Executor、Critic；C 为 Supervisor、Search Worker、Operation Worker。

- G1加热伤害20题：每个实际参与角色都收到同一组15条 Global Skill，即 `G_001–G_008` 与 `T4_001–T4_007`。相应角色注入文本为13,635字符。G1的 `T4_002` 将“手持直接加热”和“先放入微波炉再加热”并列为依观察调整的方案。其来源确有冲突：B2的A Planner、B Critic及C Supervisor/Search Worker支持先放入，A Executor、B Executor及C Operation Worker明确支持手持加热。服务器并未用任务成功证据裁定哪一种规则有效，而是把冲突保留为条件式指令。
- G3冷却伤害24题：每个实际参与角色都收到同一组12条 Global Skill，即 `G_001–G_008` 与 `T5_001–T5_004`，每角色12,409字符。G3的 `T5_001/T5_002/T5_004` 明确要求确认冷却、不以暂存替代冷却；因此不能说全局库**指示**省略冷却。不过B6本地B Critic 的 `T5_001` 包含精确语法 `cool <object> with fridge <id>`，G3合并文本改成“可用的显式冷却交互”，丢掉了这条具体命令形式。**这仅证明Skill正文的操作细节被概括；Client B Executor基础提示仍列出`cool <object> with <fridge>`命令，Critic本身也不能执行动作，因此不能据此断定措辞变化造成了失败。**

每一条伤害题的客户端、任务、episode序号、终止原因、角色注入ID、来源Skill key、注入字符数、动作序列和最后观察，见 [harm_cases.csv](harm_cases.csv) 与 [harm_cases.json](harm_cases.json)。后者还记录14个输入文件的SHA-256。

## 反复出现的行为错误

对清洗、加热、冷却三类共82道伤害题，聚合前的成功轨迹**全部**实际执行了相应的 `clean`、`heat` 或 `cool`；聚合后有60题一次也没有执行所需动作。仅依据动作日志计数，不把写在计划或Skill中的动词当作环境动作。

| 症状 | 对应伤害题 | 聚合后观察 |
|---|---:|---|
| G1加热 | 20 | 11题没有执行`heat`；15题曾把物体放入微波炉。A/B/C分别为12/6/2题。 |
| G1清洗 | 18 | 12题没有执行`clean`；C占10题。 |
| G3冷却 | 24 | 23题没有执行`cool`；19题曾把物体放入冰箱。A/B/C分别为8/7/9题。 |
| G3清洗 | 8 | 7题没有执行`clean`。 |

G3冷却的角色链进一步显示：A的8题中，Planner输出均提到`cool`，Executor轨迹仅1题真正执行；B的7题中，Critic某次输出均提到`cool`，Executor轨迹0题执行；C的9题中，仅2题的Supervisor输出提到`cool`，环境轨迹0题执行。这些只说明**控制文本与实际动作脱节的位置**，不说明提示先后关系或单条Skill的因果作用。

可复查的例子（序号为对应Global验证 `result.json.episodes` 的1-based位置）：

- G1 A加热，`pick_heat_then_place_in_recep-Potato-None-CounterTop-8`，episode 79：本地B2成功；G1轨迹两次把土豆放入微波炉，多次尝试`heat`，最后尝试`use microwave 1`并以`plan_failed`结束。G1注入了含双方案的`T4_002`；轨迹本身不能证明该Skill被遵循。
- G3 A冷却，`pick_cool_then_place_in_recep-Mug-None-CoffeeMachine-14`，episode 101：Planner要求冷却，Executor实际将杯子放入冰箱，未执行`cool`，以`plan_failed`结束；B6同题成功。
- G3 B冷却，`pick_cool_then_place_in_recep-Bread-None-DiningTable-11`，episode 102：Critic输出含冷却建议，Executor把面包放入冰箱，未执行`cool`；B6同题成功。
- G3 C冷却，`pick_cool_then_place_in_recep-Apple-None-Microwave-6`，episode 99：Supervisor先派Search Worker找冰箱里的苹果，轨迹停在打开冰箱后，没有`cool`动作，随后`worker_declared_failed`；B6同题成功。

另有14个**同客户端同题**在G1与G3都呈现“本地成功→Global失败”：A 2题、B 3题、C 9题；类别为冷却5、清洗4、双物品3、加热1、台灯1。这表明部分题在跨轮次更新后仍反复受损，尤其集中于C，但两轮本地父库不同，不能把14题理解为同一Global规则的重复试验。

## 可支持的结论与边界

本次证据较强地支持两点：①服务器把角色间相互矛盾的加热建议压成一份通用说明，G1加热类随即出现大量操作偏离；②G3冷却说明虽然写了正确检查点，实际动作仍大量缺失，且同一份全局库暴露给所有角色，不能确保跨角色交接时执行。G1在伤害题上的注入文本显著长于B2本地文本；G3冷却伤害题的全局文本反而比B6本地文本略短，故“单纯因为提示变长”无法解释两轮回落。

这是一轮每阶段一次的配对观察，不能从相关性推出某条Skill的因果伤害。下一步若需检验机制，应在冻结的独立诊断集上做单变量消融：保留角色分区对照、将`T4_002`的冲突规则拆开、对冷却Skill保留精确命令与现有概括写法作单变量比较，并逐题审阅角色交接消息。特别是执行器基础提示本来就含正确命令，不能将“Skill正文少了命令字样”直接解释为失败原因。不得直接用此验证集挑选规则后再把改进分数当独立评测。
