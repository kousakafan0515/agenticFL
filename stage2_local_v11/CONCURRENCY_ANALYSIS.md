# V11 的 Qwen 并发与运行时间评估

核对时间：2026-10-18（Asia/Shanghai）。本文件是运行方案，不是已完成的压测或额度保证。V11 与 V10 使用相同的 `qwen3.6-flash` 和相同的 134 题冻结清单；V11 尚未启动新模型调用。

## 官方限流能说明什么

- 当前阶段执行器默认使用阿里云北京兼容接口 `https://dashscope.aliyuncs.com/compatible-mode/v1`，模型名为 **`qwen3.6-flash`**。阿里云[模型页](https://help.aliyun.com/zh/model-studio/qwen3-6-flash)列出的北京额度为 **30,000 RPM、10,000,000 TPM**。这是请求/Token 吞吐额度，并非官方给出的固定“同时在途请求数”或“134 个 ALFWorld 环境并行许可”。
- [限流说明](https://help.aliyun.com/zh/model-studio/rate-limit)指出额度按主账号合并统计，其他任务使用同一账号也占用额度；服务还可能按秒级 RPS/TPS 和突发增速限流。因此不能把 30,000 RPM 直接等同于可瞬间发起 500 个请求。
- 模型名不同，额度不同：北京的快照 `qwen3.6-flash-2026-04-16` 在同一[官方模型页](https://help.aliyun.com/zh/model-studio/qwen3-6-flash)为 **600 RPM、1,000,000 TPM**。当前代码使用的是不带日期的模型名。若未来为了可重复性改为快照，必须重新核对配额并另记实验口径。
- [官方限流实践](https://help.aliyun.com/zh/model-studio/rate-limiting-best-practices)建议对突发流量做平滑启动、对请求与 Token 分别限速，并在 429/超时后调整并发。当前账号的实际限额应在运行前通过[额度查询](https://help.aliyun.com/zh/model-studio/list-quotas)或控制台核对；本文件没有读取账号凭据或发起接口调用。

## 本项目的真实瓶颈

V11 保留 V10 运行器的行为：`run_local_round.py` 每阶段启动一个 v9 冻结执行器；执行器再启动一个 ALFWorld 客户端进程，**在这个进程内逐题运行 134 题**。`run_global_validation.py` 及 `run_federated_round.py` 也顺序等待 A、B、C 的子进程。当前代码中，单客户端一阶段的在途 ALFWorld 任务数是 **1**。把 134 条任务一次传给命令行，只是固定题目列表，并不会产生 134 路并发。

从复制且哈希核对过的 v9 B1 验证结果读取的历史耗时如下；它们是参考观测，不是 V11 的预测或新验证：

| 客户端 | 134 题串行耗时 | 可直接读取的 Qwen 调用/Token | 说明 |
|---|---:|---:|---|
| A | 62.1 分钟 | 约 2,485 次、569 万 Token | 只计 `planner.usage` 与 `steps[].usage`；平均约 40 RPM、9.2 万 TPM |
| B | 43.5 分钟 | 约 1,709 次、414 万 Token | 同一统计口径；平均约 39 RPM、9.5 万 TPM |
| C | 52.2 分钟 | 未形成同口径汇总 | C 的多角色 usage 结构不同，不能把 0 误报为真实用量 |

A/B 的平均 Qwen 吞吐远低于公开的北京别名额度，**说明目前单进程串行结构比官方分钟级额度更可能限制总时间**；这是从历史记录作出的推断。它不能证明本地机器能同时承载 134 个 ALFWorld 环境，也不能排除瞬时限流、余额、网络、DeepSeek Teacher 耗时或其他任务占用额度。

## 省时运行顺序

1. 直接使用本目录已导入且仍标记为 v9 来源的 B1 种子，省去重复执行 B0 验证、B0 训练及 B1 验证。独立 Client A 从 B1→B2；联邦从三端 B1→Global1。不得把导入结果记作 V11 原生 B1。
2. 保持每个客户端内部 134 题的原始顺序、来源锁和结果校验。先在**不同客户端的独立输出目录**上实施有界并行：首轮建议同时运行 2 个客户端阶段，核对本机内存、API 429/超时、每分钟 Token 消耗和完成结果后，再考虑 3 个客户端阶段。当前 V11 控制器尚未提供此并行开关；只有完成独立输出与失败恢复校验后才能正式启用。联邦每一轮仍须等待三端本地库全部完成再聚合。
3. 如果 2–3 客户端并行后仍由本地执行时间主导，再开发**单客户端按冻结题目分片**的专用执行器。从 2 或 4 路开始实测，必要时再到 8 路；每个分片使用同一父库哈希和清单、独立结果目录。合并前按冻结次序检查 134 个唯一题目、每题结果、source lock、API-clean 和总哈希；任何分片失败都停止该阶段。现有控制器并不支持这一功能，不能直接启动 134 个现有阶段进程。
4. 为 Qwen 请求增加统一的账号级请求/Token 节流与平滑启动，再根据真实 TPM、RPM、429、延迟和本机负载调节分片数。别名额度 **不是**选择 134 路并行的充分依据。DeepSeek Teacher 和服务器聚合有自己的额度、依赖顺序与校验流程，应单独调度。

`qwen3.6-flash` 的北京 Batch API 虽有单独的批处理能力和价格，但 ALFWorld 每一步依赖上一步观察结果；不能把整条交互轨迹一次提交为离线 batch。因此本实验首先考虑跨独立客户端的受控并行，随后才是经验证的逐题分片。

本次未修改 V10/v9 执行器，也未进行账号压测、付费推理或 ALFWorld 正式评测。任何正式并行方案在运行前都要核对账号实时额度、余额、数据路径及全新输出目录。
